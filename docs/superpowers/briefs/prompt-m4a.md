# Your task: M4 Wave 1 — Agent A: world sync over the internet + robustness (spec §17.0; plan Task 1 part)
Compose project for your own server if you need one: `easycraft_a`, ports 7450 (API/socket), 7449, 7451 (console) — or use the lead's running server on 7350 read-only (never restart it).
1. **World sync by edits:** a guest generates the terrain from the world seed (the generators are deterministic; the LAN checksum test compares worlds) and receives only the host's edits: the list of changed blocks of a chunk when it comes into the guest's view, then each change as it happens (the host keeps a per-chunk edit log — find how edits are stored today: `WorldService`, `VoxelTerrainMultiplayerSynchronizer` or the voxel sync in `session.gd`/`sandbox.gd`; read the code first). Secrets (M2 Task 16) and all generated features must come out identical on the guest. Works for LAN and online alike (LAN benefits too).
2. **Pacing:** nothing big may queue ahead of player positions on the one reliable stream: send the edit lists with a per-guest byte budget per frame; check `send()` results (the spike found a full WebSocket buffer drops messages silently).
3. **Reconnect:** a guest whose connection drops rejoins the same match within 30 s, keeping its player on the host meanwhile (a "reconnecting…" overlay; after 30 s back to the menu with kind words). The host playing on when the server goes away stays as the spike made it.
4. **Plain words** for every network problem (a small table of error codes → child-friendly messages, tested).
5. **Measure** with `tools/net_test.sh` (relay and `--lan`, with `--fly`): count bytes per guest; targets: join under 2 s, under 50 kbit/s per guest while playing and flying. Record the before/after numbers (the spike's table has the before) and the load average.
Tests: edit log per chunk (add, overwrite, undo, cap), a guest world built from seed + edits equals the host's (checksum), pacing budget, reconnect state machine, error words. Notes: `docs/devlog/parts/m4-a.md`.
